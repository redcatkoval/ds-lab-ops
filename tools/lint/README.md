# ds-ops/tools/lint — линтер контрактов

## Запуск

Из `ds-ops/`:

```
python3 tools/lint/lint.py
```

Зависимостей нет, только Python 3.

Коды возврата: `0` — новых нарушений нет (замороженные и устаревшие
записи baseline код не поднимают); `1` — есть новые нарушения;
`2` — правило и контракт разошлись, проверка не проводилась.

Флаги: `--root <путь>` — переопределить область сканирования,
`--baseline <файл>` — взять другой baseline,
`--freeze` — переписать baseline текущими нарушениями.

## Откуда берутся правила

Линтер читает `rules/*.json`, а не контракт напрямую.

Контракт написан прозой для человека. Линтер, вытаскивающий правило
из прозы, на деле сопоставляет формулировки: достаточно переписать
абзац, и правило молча перестаёт срабатывать. Отдельный файл правил без
связи с контрактом расходится с ним так же молча.

Поэтому правило машиночитаемо, но несёт якорь в контракт: путь, номер
раздела и дословную цитату (`rules/action-menu.json`, поле `anchor`).
Перед проверкой линтер ищет цитату в контракте. Не находит —
останавливается с кодом 2 и сообщает о расхождении. Молчаливого
расхождения не остаётся: либо правило проверено, либо проверка не
проводилась и об этом сказано.

Статус контракта линтер читает из шапки и печатает. Пока он не
`enforced`, вывод содержит строку о том, что CI мерж не блокирует.

### Как считаются действия (правило 4.1)

Контракт описывает плоский список `actions`, код пока передаёт `groups`.
Линтер понимает обе формы: берёт `actions`, если он есть, иначе
суммирует действия по всем группам `groups`.

Действия из условного спреда (`...(условие ? [{…}] : [])`) считаются
присутствующими. На текущем коде выбор ничего не меняет: вызовов с одним
действием 45 при любом из двух прочтений.

Если хоть одна часть списка собирается в рантайме — `groups` или
`actions` переменной, группа переменной, сборка через `.map()`,
пропсы спредом, — вызов уходит в «НЕ ПРОВЕРЕНО», а не в «чисто».
Таких 10 из 115.

## Baseline

`baseline.json` — существующие нарушения, зафиксированные как долг.
Линтер их показывает отдельным списком, ошибкой не считает и код
возврата из-за них не поднимает. Всё сверх baseline — новое, код 1.

### Как запись переживает сдвиг строк

Номер строки в опознании не участвует. Ключ записи — тройка
`rule` + `file` + `fingerprint`, где `fingerprint` это первые 16 hex
от sha256 имени тега и его атрибутов со схлопнутыми пробелами.
Отпечаток не зависит ни от положения вызова в файле, ни от переносов
строк и отступов внутри самого тега.

`line_hint` в записи есть, но при сверке не читается — он только для
человека, чтобы быстрее найти место.

Кратность решается полем `count`: сколько одинаковых вызовов заморожено
в этом файле. Найдено столько же — все заморожены. Найдено больше —
избыток считается новым. Найдено меньше — запись помечена как устаревшая.
Поэтому одинаковые вызовы не схлопываются в один (нарушение не теряется)
и не засчитываются дважды.

### Когда отпечаток меняется

Если атрибуты вызова переписали — отпечаток другой. Тогда прежняя запись
покажется устаревшей, а изменённый вызов — новым нарушением. Это
осознанный размен: переформатирование отпечаток не ломает, а правка
атрибутов и должна проходить через ревью заново.

### Устаревшие записи

Если замороженное нарушение исправили, линтер печатает блок
«BASELINE УСТАРЕЛ» с отпечатком и предложением вычеркнуть запись.
Ошибкой это не считается, код возврата остаётся 0: код стал лучше,
устарел файл долга. Линтер `baseline.json` не правит — вычёркивает
человек.

## Границы проверки

Разбор статический, по тексту `.tsx`. Линтер видит атрибуты, записанные
в теге. Пропсы, приходящие спредом (`{...props}`), он засчитать не может
и печатает их отдельным списком «не проверено» — это не «нарушений нет»,
а «неизвестно».

Директория самого компонента (`components/common/action-menu`) из
области исключена: там `variant` объявлен, а не передан.
