## 1. Назначение

ActionMenu — меню действий над одной сущностью, свёрнутое под один
триггер. Раскрывается по нажатию, содержит плоский список действий,
каждое из которых либо ведёт по ссылке, либо вызывает обработчик.

Применяется в заголовке секции, в строке таблицы и в карточке — там, где
у сущности есть несколько действий и все они не помещаются в интерфейс
кнопками.

Наблюдение: используется в 104 файлах, 115 вхождений тега.

## 2. Когда не использовать

**Решение.** При одном действии ActionMenu не применяется. Нужна
иконочная или текстовая кнопка.

Одно действие под меню — это два клика вместо одного.

Наблюдение, перемерено 2026-09-02: сейчас так в 45 вызовах
из 106 разобранных. Ещё 1 вызов передаёт пустой список —
`routes/products/product-create/components/product-create-details-form/components/product-create-details-media-section/product-create-details-media-section.tsx:303`.

## 3. API

**Решение.** Плоский список действий вместо групп.

Раздел описывал целевое состояние, пока компонент ему не соответствовал.
С 2026-09-02 он описывает действительность: тип в коде совпадает
с приведённым здесь.

```ts
type Action = {
  icon: ReactNode
  label: string
  disabled?: boolean
  disabledTooltip?: string | ReactNode
  destructive?: boolean
} & (
  | { to: string; onClick?: never }
  | { onClick: () => void; to?: never }
)

type ActionMenuProps = PropsWithChildren<{
  actions: Action[]
}>
```

Сверено с `action-menu.tsx:9-34` — расхождений нет.

Путь, которым это состояние получено:

| изменение | коммит |
|---|---|
| `destructive?: boolean` добавлен в `Action` | `eb766c31` |
| `groups: ActionGroup[]` → `actions: Action[]`, тип `ActionGroup` удалён | `219a8275` |
| `variant?: "transparent" \| "primary"` удалён | `219a8275` |

**Решение.** `variant` у триггера не используется. Выполнено: проп
удалён, умолчание зашито — `IconButton` с `variant="transparent"`
(`action-menu.tsx:39`).

`children` остаётся без изменений. Наблюдение: передан один раз —
`routes/orders/order-detail/components/order-summary-section/order-summary-section.tsx:212`,
подставляет `Button` вместо `IconButton` по умолчанию.

Имя `actions` для поля выбрано при записи контракта; в разговоре
решение звучало как «плоский список действий».

Поля `icon`, `label`, `disabled`, `disabledTooltip` и взаимоисключающая
пара `to` / `onClick` сохранены как были (`action-menu.tsx:9-30`).

**Следствие для дерева доступности.** Вместе с группами из разметки
исчез элемент `role="group"`. Потеря принята решением
[DEC-012](../decisions/DEC-012-ploskiy-spisok-bez-role-group.md); там же
измерено, что навигация с клавиатуры и объявление пунктов не задеты.

## 4. Правила

Правила двух видов, и оба обязательны.
**[проверяется линтером]** — линтер находит нарушение сам и блокирует
мерж. **[проверяется человеком]** — правило обязательно ровно так же,
но статически не ловится, поэтому его проверяют на ревью.
Отдельно помечена одна **[рекомендация]** — она необязательна.

### 4.1 Число действий

**Решение.** Действий два или больше. Ноль и одно запрещены. **[проверяется линтером]**

**Решение.** До пяти действий. **[рекомендация]**

Это единственная рекомендация в контракте. Превышение не ошибка:
ни линтер, ни ревью его не блокируют. Больше пяти — повод пересмотреть
состав меню.

Правило о двух действиях линтер проверяет только там, где список задан
литералом. Наблюдение: из 115 вхождений список собирается в рантайме
в 10 (перечислены в фактах, раздел «Чего этот способ не видит»).
Эти 10 остаются на ревью.

### 4.2 Разделители

**Решение.** Разделитель ставится между всеми действиями. Группировки
нет. **[выполняется по построению]**

> Метка изменена 2026-09-02. Была **[проверяется линтером]** —
> проверять было нечего, пока разделитель ставился между группами.
> Теперь проверять нечего по обратной причине: нарушить нельзя.

Разделитель — свойство компонента, не вызова. В API поля для него нет.
Компонент ставит его между соседними действиями и только там —
`action-menu.tsx:86` и `:112`, условие `!isLastAction`.

Проверено рендером 2026-09-02 на восьми историях витрины: во всех
разделителей ровно на один меньше, чем пунктов.

### 4.3 Разрушающее действие

**Решение.** Действие с `destructive: true` всегда последнее в списке.
**[проверяется линтером]**

> В линтере не реализовано, но с 2026-09-02 **стало выразимо**: признак
> `destructive` в типе есть (`action-menu.tsx:20`), и порядок элементов
> в литеральном списке разбирается тем же способом, что и их число.
> Это единственное правило, которое можно реализовать прямо сейчас.

**Решение.** Разрушающее действие помечено красным.
**[выполняется по построению]**

> Метка изменена 2026-09-02. Цвет назначает компонент по признаку
> `destructive` — `action-menu.tsx:76` и `:98`, класс
> `text-ui-fg-error [&_svg]:text-ui-fg-error`. Вызов на цвет не влияет
> и отменить его не может.

Токен назван решением
[DEC-011](../decisions/DEC-011-krasnyy-v-menyu-fg-error.md): `fg-error`,
токен переднего плана. Раздел 5 больше не оставляет его неназначенным.

**Оговорка, без которой правило читается неверно.** «По построению»
здесь означает: *если* признак проставлен. Проставить его обязан вызов,
и сейчас он проставлен у 1 действия из примерно 70 — см. раздел 6.

**Решение.** Разрушающее действие вызывает подтверждение.
**[проверяется человеком]**

Статической проверкой не покрывается: наличие подтверждения внутри
обработчика по типу не выражено. См. раздел 7.

### 4.4 Остальные действия

**Решение.** Действие, не помеченное `destructive`, либо открывает
шторку, либо переходит по ссылке. **[проверяется человеком]**

Переход по ссылке проверяется по наличию `to`. Открытие шторки внутри
`onClick` статической проверкой не отличается от любого другого
обработчика.

Наблюдение, перемерено 2026-09-02: из 192 действий в 106 разобранных
вхождениях 102 задают `to`, 90 — `onClick`. Действий без того и другого
нет.

### 4.5 Триггер

**Решение.** Триггер без рамки. **[выполняется по построению]**

> Метка изменена 2026-09-02. Проп `variant` удалён из `ActionMenuProps`
> (`action-menu.tsx:32-34`, коммит `219a8275`). Вид триггера из вызова
> больше не выбирается: умолчание зашито — `IconButton` с
> `variant="transparent"` (`action-menu.tsx:39`).

Правило выполняется не потому, что его соблюдают, а потому, что
нарушить его нечем. Единственный вызов, который передавал
`variant="primary"` — `components/data-table/data-table.tsx` — исправлен
тем же коммитом, и его запись ушла из baseline.

### Что делать с проверкой `action-menu/no-trigger-variant`

**Решение, 2026-09-02: проверку в её нынешнем виде убрать и заменить.**
Не выполнено — правка линтера отдельным шагом.

**Почему убрать.** Проверка ищет проп `variant` в вызовах `<ActionMenu`.
Такого пропа в типе нет, и любой вызов, который его передаст, отвергнет
компилятор — проверено на этой же правке: `tsgo` дал ошибку
`Property 'variant' does not exist`, пока проп не убрали из
`data-table.tsx`. Проверка не находит ничего и найти не может.
Мёртвая проверка хуже отсутствующей: она попадает в строку «Правила:»
каждого прогона и завышает представление о том, что машина стережёт.

**Почему заменить, а не просто удалить.** Само правило не исчезло, оно
переехало из вызовов в компонент. Формулировка выше — «проверяется
отсутствием у компонента props, управляющих видом триггера» — с самого
начала описывала проверку на компоненте; проверка вызовов была
временным заменителем, пока проп существовал. Теперь заменитель мёртв,
а настоящая проверка стала возможна: читать `ActionMenuProps` в
`action-menu.tsx` и падать, если там появился проп вида триггера.

Она стережёт причину, а не следствие. Нынешняя ловит вызов, который
воспользовался вернувшимся пропом, — то есть срабатывает после того,
как правило уже нарушено в компоненте.

**Чего это стоит.** Линтер сейчас умеет одно: разбирать теги
`<ActionMenu` в области сканирования. Чтение объявления типа — другой
разбор и другая область (один файл вместо дерева). Это не переделка
правила, а новый вид правила.

**Отвергнутая альтернатива — оставить как есть.** Ноль работы, но
проверка навсегда останется строкой в отчёте, которая ничего не значит.
Если оставлять, честнее было бы пометить её в отчёте как мёртвую,
а это та же работа, что и замена, только без пользы.

**До замены правило 4.5 не считается проверяемым машиной.** В разделе
«Статусы» оно учтено как выполняемое по построению, а не как
проверяемое.

## 5. Токены

**Отступы** — по DEC-007 (`ds-ops/decisions/DEC-007-shkala-devyat-znacheniy.md`):
девять значений 2, 4, 6, 8, 12, 16, 24, 32, 64 px. Произвольные значения

ступенями.

Наблюдение: в компоненте радиусов нет ни одного.

**Цвет.** Наблюдение, перемерено 2026-09-02: литеральных цветов
в компоненте нет. Цвет задан токенами `text-ui-fg-subtle` (`:74`, `:96`),

Красный цвет разрушающего действия (правило 4.3) — токен `fg-error`,
назначен решением
[DEC-011](../decisions/DEC-011-krasnyy-v-menyu-fg-error.md) 2026-09-02.
Выбран по роли: `fg-error` — токен переднего плана, `button-danger` —
токен заливки. Прежняя формулировка «конкретный токен не назначен»
больше не действует.

Наблюдение к семейству: измерение всех красных токенов системы —
`ds-ops/tokens/red-usage.json`.

Что с этим делать — раздел 7.4.

**3. Десять вызовов собирают список в рантайме.**

Не изменилось: было 10, осталось 10. Шаг к однородной форме
(коммит `c05fe3e4`) сделал их одинаковыми по виду, но не сделал
разбираемыми — список по-прежнему приходит переменной. Для линтера они
не «чисто», а «неизвестно».

## 7. Открытые зависимости

**7.1 Формулировка про триггер.** Правило 4.5 записано как «без рамки».
Точная формулировка зависит от контракта на кнопку, которого пока нет.
До него правило 4.5 читать как запрет на выбор вида триггера из вызова,
а не как описание вида.

**7.2 Подтверждение у разрушающих действий.** Не проверено поштучно,
есть ли подтверждение у всех 70.

Пофайловый признак (наличие вызова `prompt(` в файле вызова) даёт:
47 из 70 — в файле есть `prompt(`; 22 — обработчик есть, `prompt(` в
файле нет; 1 — не обработчик, а ссылка `to`.

Признак пофайловый, не по действию: файл может вызывать `prompt(` для
одного действия и не вызывать для другого. Поштучная проверка требует
разбора обработчиков и не проведена.

**7.3 Токен красного цвета** для правила 4.3 назначен 2026-09-02 —
`fg-error`, решение
[DEC-011](../decisions/DEC-011-krasnyy-v-menyu-fg-error.md). Зависимость
закрыта.

**7.4 Кто проставляет `destructive` у остальных 69.** Признак есть,
но не проставлен (раздел 6, пункт 2). Открыты три вопроса сразу:
проставлять ли его сплошь или по мере правок; считать ли отсутствие
признака нарушением контракта; и можно ли поручить опознание линтеру,
если опознавать приходится по иконке и метке, а не по типу.

**7.5 Замена проверки 4.5.** Решение принято (раздел 4.5), не выполнено.
Требует нового вида правила в линтере — чтения объявления типа, а не
разбора тегов.

**7.6 Расхождение с копией компонента.** В `packages/plugins/draft-order/`
живёт копия `ActionMenu` с 6 вызовами, вне области линтера и вне этого
контракта. После правок 2026-09-02 у копии и оригинала разный API.
См. [Q-015](../questions/Q-015-kopiya-komponenta-v-plagine.md).
