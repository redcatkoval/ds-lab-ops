## 1. Назначение

ActionMenu — меню действий над одной сущностью, свёрнутое под один
триггер. Раскрывается по нажатию, содержит плоский список действий,
каждое из которых либо ведёт по ссылке, либо вызывает обработчик.

Применяется в заголовке секции, в строке таблицы и в карточке — там, где
у сущности есть несколько действий и все они не помещаются в интерфейс
кнопками.

Наблюдение, перемерено 2026-09-08: используется в 83 файлах,
90 вхождений тега. На 2026-09-02 было 104 файла и 115 вхождений;
разница — 25 меню, заменённых кнопками по DEC-015.

### Разрушающее действие

**Решение, 2026-09-02.** Разрушающим считается действие, которое **само**
производит необратимое изменение — такое, последствия которого
пользователь не может отменить тем же меню.

Два условия, и оба обязательны:

1. **Необратимость.** Последствие нельзя отменить соседним пунктом того
   же меню. Признак — необратимость для человека за экраном, а не тип
   операции: не важно, удаляет ли действие запись, отзывает доступ или
   двигает деньги.
2. **Непосредственность.** Изменение производит само нажатие пункта.
   Переход к форме, в которой такое изменение можно произвести, —
   не разрушающее действие: нажатие пункта ничего не меняет, а форму
   ещё можно закрыть.

Из определения следует, в частности:

- удаление, отзыв и отмена — разрушающие: нажатие пункта производит
  изменение, и ни одно из них не отменяется соседним пунктом;
- тумблер — не разрушающий, даже если выключает что-то важное:
  тот же пункт меню возвращает прежнее состояние;
- редактирование — не разрушающее: форма открывается заново;
- **переход к форме возврата платежа — не разрушающее**, хотя сам
  возврат необратим. Опасность в форме, а не в переходе.

Практическое следствие второго условия: действие, заданное через `to`,
разрушающим не бывает — ссылка ведёт на экран, а не производит
изменение. Без этого условия по той же логике пришлось бы красить
«Редактировать»: за той формой тоже стоят необратимые изменения.

Наблюдение, 2026-09-02: из 76 действий с признаком все 76 заданы через
`onClick`; действий с признаком и `to` не осталось.

Определение решает случаи, которые прежняя формулировка не решала:
раньше разрушающее опознавалось по иконке `Trash` и метке
`actions.delete`, то есть по внешнему виду. Разбор 182 действий
2026-09-02 нашёл четыре пограничных случая, на которых опознание
по виду расходится с опознанием по определению: отзыв ключа API
(разрушающее, признак стоит), переход к возврату платежа
(не разрушающее по второму условию), переключатель налога
(не разрушающее по первому) и `actions.disable`, который на деле
удаляет — [Q-016](../questions/Q-016-metka-disable-pri-udalenii.md).

Разрушающее действие помечается `destructive: true`. Ставит признак
вызов — компонент опознать разрушающее не может.

## 2. Когда не использовать

**Решение.** При одном действии ActionMenu не применяется. Нужна
иконочная или текстовая кнопка.

Одно действие под меню — это два клика вместо одного.

**Чем заменять — образец.** Вид кнопки задан
[DEC-015](../decisions/DEC-015-obrazec-zameny-menyu-na-knopku.md):
`<Button size="small" variant="secondary">`, с `asChild` и `Link` для
перехода, без иконки. Образец найден обходом 17 шапок секций
(обход 2026-09-02, DEC-015), а не придуман. Первое применение —
`product-media-section.tsx:89`, коммит `ae40f47a`.

**Основание, добавлено 2026-09-02.** Это частный случай
[DEC-014](../decisions/DEC-014-osnovnye-knopkami-prochie-v-menyu.md):
основные действия выносятся кнопками, прочие уходят в меню. Если
действие одно, оно по определению основное — элемент существует ради
него, — и потому кнопка, а не меню.

До DEC-014 правило читалось счётным: «меньше двух — нарушение». Теперь
у него есть причина, и она не в числе пунктов.

**Исключение — разрушающее действие.** Если единственное действие
разрушающее, меню остаётся: основание — раздел 4.1 и
[DEC-017](../decisions/DEC-017-menyu-na-odno-razrushayushchee.md).
Правило этого раздела выведено из DEC-014 — единственное действие
считается основным, потому что элемент существует ради него. Ради
удаления элемент не существует, и посылка не выполняется.

Наблюдение, перемерено 2026-09-08: сейчас так в 20 вызовах
из 80 разобранных, и 12 из этих 20 — под исключением выше.
Ещё 1 вызов передаёт пустой список —
`routes/products/product-create/components/product-create-details-form/components/product-create-details-media-section/product-create-details-media-section.tsx:296`.

## 3. API

**Решение.** Плоский список действий вместо групп.

Раздел описывал целевое состояние, пока компонент ему не соответствовал.
С 2026-09-02 он описывает действительность: тип в коде совпадает
с приведённым здесь.

```ts
type Action = {
  icon: ReactNode
  label: string
  disabled?: boolean
  disabledTooltip?: string | ReactNode
  destructive?: boolean
} & (
  | { to: string; onClick?: never }
  | { onClick: () => void; to?: never }
)

type ActionMenuProps = PropsWithChildren<{
  actions: Action[]
}>
```

Сверено с `action-menu.tsx:9-34` — расхождений нет.

**Решение, 2026-09-08. Набор полей `ActionMenuProps` закрыт: в типе нет
полей, кроме перечисленных выше. [проверяется линтером]**

Проверка — `action-menu/props-closed`. Она читает объявление типа
в компоненте и сверяет состав полей с приведённым здесь: любое поле
сверх списка — нарушение, отсутствие поля из списка — тоже.

Список разрешённого и якорь правила — один и тот же текст, блок `ts`
выше. Поэтому разъехаться молча они не могут ни в одну сторону:
правка объявления в контракте разрывает якорь, и линтер встаёт
с кодом 2; правка типа в коде даёт нарушение и код 1. Чтобы добавить
проп, надо изменить оба, и это видно в одном коммите.

Форма объявления тоже часть условия: правая часть — `PropsWithChildren`
от одного объектного литерала, и ничего больше. Пересечение
(`PropsWithChildren<{…}> & Прочее`) правило считает нарушением формы,
не заглядывая внутрь: иначе поле можно было бы внести мимо проверяемого
списка.

Путь, которым это состояние получено:

| изменение | коммит |
|---|---|
| `destructive?: boolean` добавлен в `Action` | `eb766c31` |
| `groups: ActionGroup[]` → `actions: Action[]`, тип `ActionGroup` удалён | `219a8275` |
| `variant?: "transparent" \| "primary"` удалён | `219a8275` |

**Решение.** `variant` у триггера не используется. Выполнено: проп
удалён, умолчание зашито — `IconButton` с `variant="transparent"`
(`action-menu.tsx:39`).

`children` остаётся без изменений. Наблюдение: передан один раз —
`routes/orders/order-detail/components/order-summary-section/order-summary-section.tsx:212`,
подставляет `Button` вместо `IconButton` по умолчанию.

Имя `actions` для поля выбрано при записи контракта; в разговоре
решение звучало как «плоский список действий».

Поля `icon`, `label`, `disabled`, `disabledTooltip` и взаимоисключающая
пара `to` / `onClick` сохранены как были (`action-menu.tsx:9-30`).

**Следствие для дерева доступности.** Вместе с группами из разметки
исчез элемент `role="group"`. Потеря принята решением
[DEC-012](../decisions/DEC-012-ploskiy-spisok-bez-role-group.md); там же
измерено, что навигация с клавиатуры и объявление пунктов не задеты.

## 4. Правила

Правила двух видов, и оба обязательны.
**[проверяется линтером]** — линтер находит нарушение сам и блокирует
мерж. **[проверяется человеком]** — правило обязательно ровно так же,
но статически не ловится, поэтому его проверяют на ревью.
Отдельно помечена одна **[рекомендация]** — она необязательна.

### 4.1 Число действий

**Решение.** Действий два или больше. Ноль и одно запрещены. **[проверяется линтером]**

**Решение.** До пяти действий. **[рекомендация]**

Это единственная рекомендация в контракте. Превышение не ошибка:
ни линтер, ни ревью его не блокируют. Больше пяти — повод пересмотреть
состав меню.

**Исключение, 2026-09-08.** Вызов, в котором ровно одно действие
и это действие несёт `destructive: true`, нарушением правила 4.1
не считается. **[проверяется линтером]**

Основание — [DEC-017](../decisions/DEC-017-menyu-na-odno-razrushayushchee.md):
правило 4.1 выведено из [DEC-014](../decisions/DEC-014-osnovnye-knopkami-prochie-v-menyu.md),
а на разрушающем действии посылка DEC-014 не выполняется. Секция
существует не ради того, чтобы её удалили.

**Формулировка узкая нарочно.** Исключение говорит про **ровно одно**
действие. Меню из нескольких разрушающих под него не подводится —
и не нуждается в этом: там действий больше одного, и правило 4.1
не нарушено само по себе. Записать исключение шире значило бы
разрешить случай, которого в коде нет и который никто не смотрел.

Пустой список исключением не покрыт: ноль действий остаётся
нарушением. Чем заменить такое меню — вопрос к продукту, раздел 6,
пункт 1.

Правило о двух действиях линтер проверяет только там, где список задан
литералом. Наблюдение, перемерено 2026-09-08: из 90 вхождений список
собирается в рантайме в 10 (перечислены в фактах, раздел «Чего этот
способ не видит»).
Эти 10 остаются на ревью.

### 4.2 Разделители

**Решение.** Разделитель ставится между всеми действиями. Группировки
нет. **[выполняется по построению]**

> Метка изменена 2026-09-02. Была **[проверяется линтером]** —
> проверять было нечего, пока разделитель ставился между группами.
> Теперь проверять нечего по обратной причине: нарушить нельзя.

Разделитель — свойство компонента, не вызова. В API поля для него нет.
Компонент ставит его между соседними действиями и только там —
`action-menu.tsx:86` и `:112`, условие `!isLastAction`.

Проверено рендером 2026-09-02 на восьми историях витрины: во всех
разделителей ровно на один меньше, чем пунктов.

### 4.3 Разрушающее действие

**Решение, уточнено 2026-09-02.** Действия с `destructive: true` идут
последними в списке. Между собой — в любом порядке.
**[проверяется линтером]**

> Прежняя формулировка — «действие с `destructive: true` всегда последнее» —
> молча предполагала, что такое действие одно. Это была дыра: меню
> с двумя разрушающими действиями формально нарушало правило, каким бы
> ни был их порядок. Разбор 2026-09-02 такой случай нашёл —
> `api-key-general-section.tsx`, удаление ключа и отзыв ключа в одном
> меню.

Проверяемое условие: в списке нет действия без признака после действия
с признаком. Именно оно, а не «разрушающее последнее»: несколько
разрушающих подряд правилу не противоречат.

Признак читается среди полей верхнего уровня действия — вложенные
объекты не смотрятся. Действия из условного спреда считаются
присутствующими, так же как в правиле 4.1.

Проверено 2026-09-02 на четырёх случаях порядка: «обычное, разр., разр.»
— чисто; «разр., разр., обычное» — нарушение; «разр., обычное, разр.» —
нарушение; «два обычных» — чисто. Отдельно проверено, что правило
не зашито на результат: перестановка действий в копии реального вызова
даёт нарушение.

> Реализовано 2026-09-02 — `action-menu/destructive-last`. Признак
> `destructive` в типе есть (`action-menu.tsx:20`), порядок элементов
> в литеральном списке разбирается тем же способом, что и их число.

**Решение.** Разрушающее действие помечено красным.
**[выполняется по построению]**

> Метка изменена 2026-09-02. Цвет назначает компонент по признаку
> `destructive` — `action-menu.tsx:76` и `:98`, класс
> `text-ui-fg-error [&_svg]:text-ui-fg-error`. Вызов на цвет не влияет
> и отменить его не может.

Токен назван решением
[DEC-011](../decisions/DEC-011-krasnyy-v-menyu-fg-error.md): `fg-error`,
токен переднего плана. Раздел 5 больше не оставляет его неназначенным.

**Оговорка, без которой правило читается неверно.** «По построению»
здесь означает: *если* признак проставлен. Проставить его обязан вызов;
на 2026-09-08 он стоит у 76 действий — раздел 6, пункт 2.

> Переписано 2026-09-08. Прежняя редакция говорила «проставлен
> у 1 действия из примерно 70» — состояние до 2026-09-02, когда признака
> в типе ещё не было. К вечеру того же дня он проставлен у 76, и с тех
> пор оговорка описывала не действительность, а тот день, когда её
> писали. Число «примерно 70» было и оценкой числа разрушающих действий,
> а не их описью.

Оговорка при этом не отменяется, только меняет смысл: компонент красит
то, что помечено, и пометить за автора не может. Непроставленный признак
ему невидим — 7.4.

**Решение.** Разрушающее действие вызывает подтверждение.
**[проверяется человеком]**

Статической проверкой не покрывается: наличие подтверждения внутри
обработчика по типу не выражено. См. раздел 7.

### 4.4 Остальные действия

шторку, либо переходит по ссылке. **[проверяется человеком]**

### Что делать с проверкой `action-menu/no-trigger-variant`

**Решение, 2026-09-02: проверку в её нынешнем виде убрать и заменить.**
**Выполнено 2026-09-08.** Проверка снята 2026-09-02, замена написана
2026-09-08 — `action-menu/props-closed`.

**Почему убрать.** Проверка ищет проп `variant` в вызовах `<ActionMenu`.
Такого пропа в типе нет, и любой вызов, который его передаст, отвергнет
компилятор — проверено на этой же правке: `tsgo` дал ошибку
`Property 'variant' does not exist`, пока проп не убрали из
`data-table.tsx`. Проверка не находит ничего и найти не может.
Мёртвая проверка хуже отсутствующей: она попадает в строку «Правила:»
каждого прогона и завышает представление о том, что машина стережёт.

**Почему заменить, а не просто удалить.** Само правило не исчезло, оно
переехало из вызовов в компонент. Формулировка выше — «проверяется
отсутствием у компонента props, управляющих видом триггера» — с самого
начала описывала проверку на компоненте; проверка вызовов была
временным заменителем, пока проп существовал. Теперь заменитель мёртв,
а настоящая проверка стала возможна: читать `ActionMenuProps` в
`action-menu.tsx` и падать, если там появился проп вида триггера.

Она стережёт причину, а не следствие. Нынешняя ловит вызов, который
воспользовался вернувшимся пропом, — то есть срабатывает после того,
как правило уже нарушено в компоненте.

**Чего это стоит.** Линтер сейчас умеет одно: разбирать теги
`<ActionMenu` в области сканирования. Чтение объявления типа — другой
разбор и другая область (один файл вместо дерева). Это не переделка
правила, а новый вид правила.

**Отвергнутая альтернатива — оставить как есть.** Ноль работы, но
проверка навсегда останется строкой в отчёте, которая ничего не значит.
Если оставлять, честнее было бы пометить её в отчёте как мёртвую,
а это та же работа, что и замена, только без пользы.

**Чем правило 4.5 покрыто теперь.** Замена написана не под 4.5,
а под раздел 3: `action-menu/props-closed` проверяет состав полей
`ActionMenuProps` и падает на любом новом поле, а не только на пропе
вида триггера. Правило 4.5 покрыто **следствием**: проп вида не
появится, потому что не появится никакой.

Так вышло не по недосмотру, а потому, что «проп вида триггера» машине
не опознать. Опознавать по имени — `variant`, `size`, `className` —
значит завести перечень догадок: проп под именем, которого в перечне
нет, пройдёт мимо. Это тот самый способ, из-за которого 7.4 оставлена
нерешённой. Закрытый набор полей догадки не требует: разрешённое взято
из раздела 3 дословно.

**Правило 4.5 остаётся [выполняется по построению].** Метка не меняется:
машина стережёт причину — то, что вид триггера из вызова не выбирается,
потому что в типе нет и не появится пропа. Записать 4.5 в проверяемые
значило бы обещать в отчёте больше, чем проверка делает, — то самое,
за что снята `no-trigger-variant`.

### 4.6 Положение триггера

**Решение, 2026-09-02.** Триггер меню — последний элемент в ряду
элементов управления. После кнопок основных действий, включая `Create`.
**[проверяется человеком]**

Основание — [DEC-013](../decisions/DEC-013-trigger-posledniy-v-ryadu.md):
меню содержит прочие действия над существующим, кнопка `Create` создаёт
новое. Что именно считается основным действием и потому выносится
кнопкой — [DEC-014](../decisions/DEC-014-osnovnye-knopkami-prochie-v-menyu.md). Крайнее положение отделяет меню от кнопок без дополнительной
формы, поэтому правило 4.5 остаётся в силе и `variant` не возвращается.

**Почему не линтером.** Правило говорит не о вызове, а о его окружении.
Чтобы проверить его машиной, надо разобрать раскладку соседних
элементов: найти родителя вызова, убедиться, что это ряд, перечислить
его детей в порядке следования и понять, какие из них элементы
управления. Ни одного из четырёх шагов линтер сейчас не умеет — он
разбирает тег и его атрибуты, а не дерево вокруг.

Отдельная трудность: «ряд» — не синтаксическая сущность. Это `div`
с определёнными классами раскладки, и опознавать его пришлось бы
по классам, то есть догадкой. Правило, проверяемое догадкой, контракт
не заводит — то же соображение, что в 7.4.

Правило остаётся на ревью.

**Исключение, 2026-09-02.** Если триггер задан вызовом через
`children`, меню замещает кнопку основного действия и остаётся на её
месте.

Признак различим машинно: `children` передан. Такой вызов один
из 90 (перемерено 2026-09-08) —
`routes/orders/order-detail/components/order-summary-section/order-summary-section.tsx:212`.

Основание — соседний код того же вызова (`:203`): при одном получаемом
возврате рисуется обычная `Button`, при нескольких — меню на её месте.
То есть меню здесь не свалка прочего, а разрешение неоднозначности
одного основного действия: «принять возврат» становится списком, когда
возвратов несколько. По [DEC-014](../decisions/DEC-014-osnovnye-knopkami-prochie-v-menyu.md)
это основное действие, и по DEC-013 в конец ряда оно не уходит.

Перенести такое меню в конец значило бы оторвать его от места, где
стоит его же однокнопочный вариант.

**Границы.** Правило о порядке, не о виде и не о расстояниях. Там, где
ряда нет — в заголовке секции, в строке таблицы, в карточке, — меню
обычно единственный элемент, и правило ни к чему не обязывает.

([Q-016](../questions/Q-016-metka-disable-pri-udalenii.md)). Не получили
переход к возврату платежа и переключатель налога.

Порядок при этом не нарушился нигде: правило 4.3 на всех 90 вызовах
даёт ноль нарушений (прогон 2026-09-08).

**Что осталось от этого пункта.** Не сами действия, а невозможность
проверить их машиной: линтер видит проставленный признак, но не видит
непроставленного — 7.4.

**3. Вызовы, по которым проверка не может дать ответ.**

Их два вида, и это не одно и то же «неизвестно».

| правило | вызовов без ответа | чего не хватает |
|---|---:|---|
| 4.1, число действий | 10 | списка: приходит переменной |
| 4.3, порядок | 15 | элементов: список есть, но состав элементов неизвестен |

**Множества вложены, а не пересекаются частично.** Проверено прогоном
2026-09-02 и повторно 2026-09-08: все 10 вызовов правила 4.1 входят
в 15 вызовов правила 4.3; вызовов, неизвестных только правилу 4.1, —
ноль. Это ожидаемо: если списка нет вовсе, то и элементов нет.

**Первые 10 — список приходит переменной.** Не изменилось с 2026-08:
было 10, осталось 10. Шаг к однородной форме (коммит `c05fe3e4`) сделал
их одинаковыми по виду, но не разбираемыми.

**Ещё 5 — список известен, элементы нет.** Правилу 4.1 они не мешают:
оно считает элементы и не смотрит внутрь. Правилу 4.3 нужно знать про
каждый элемент, разрушающий он или нет, а форма элемента ответа не даёт:

| вызов | форма элемента |
|---|---|
| `claim-inbound-item.tsx` | `!showReturnReason && { … }`, список закрыт `.filter(Boolean) as Action[]` |
| `exchange-inbound-item.tsx` | то же |
| `return-item.tsx` | то же |
| `order-edit-item.tsx` | `...[ !isItemRemoved ? { … } : { … } ]` |
| `tax-region-card.tsx` | `...([ !hasParent && { … }, … ])` |

Объект внутри есть, но добраться до его полей, не вычисляя условие,
нельзя. Записать такой вызов в «чисто» было бы враньём: неизвестный
элемент мог бы оказаться разрушающим и стоять перед обычным.

**Что из этого следует.** Разница между 10 и 15 — не недоработка
линтера, а цена формы записи в вызовах. Первые 10 лечатся тем, чтобы
список задавался литералом; вторые 5 — тем, чтобы условие стояло
вокруг списка (`...(cond ? [x] : [])`), а не внутри элемента
(`cond && x`). Обе правки — в вызовах, не в проверке. Решения о том,
делать ли их, нет; см. 7.7.

## 7. Открытые зависимости

**7.1 Формулировка про триггер.** Правило 4.5 записано как «без рамки».
Точная формулировка зависит от контракта на кнопку, которого пока нет.
До него правило 4.5 читать как запрет на выбор вида триггера из вызова,
а не как описание вида.

**Дополнено 2026-09-02.** У правила нашлась вторая незакрытая сторона:
контракт молчал о положении меню в раскладке. Единственный вызов,
передававший `variant="primary"`, оказался единственным местом, где меню
стоит в ряду кнопок, и без рамки там стало хуже —
[Q-017](../questions/Q-017-trigger-v-ryadu-knopok.md). Довод «один
случай из 115, значит ошибка» был доводом по частоте, а не по существу.
База с тех пор — 90 вхождений (2026-09-08), случай по-прежнему один.

**Закрыто в тот же день правилом 4.6** и решением
[DEC-013](../decisions/DEC-013-trigger-posledniy-v-ryadu.md): меню стоит
последним в ряду, и тогда рамка не нужна. Удаление `variant` при этом
осталось верным: оно сняло с второстепенного элемента вес основного.
Несостыковка была в положении, а не в виде — формулировка Q-017
приведена к этому 2026-09-02 по
[DEC-016](../decisions/DEC-016-formulirovki-cherez-nesostykovku.md). Из трёх исходов Q-017 выбран
не первый (вернуть рамку), а близкий ко второму — исправляется
положение, а не вид. Первая сторона 7.1 остаётся открытой: точная
формулировка «без рамки» по-прежнему ждёт контракта на кнопку.

**7.2 Подтверждение у разрушающих действий.** Не проверено поштучно,
есть ли подтверждение у всех 76.

Пофайловый признак (наличие вызова `prompt(` в файле вызова), перемерено
2026-09-08:

| | действий |
|---|---:|
| в файле есть `prompt(` | 53 |
| в файле нет `prompt(` | 23 |
| задано ссылкой `to`, а не обработчиком | 0 |

> Прежние числа — 47, 22 и 1 — считались от 70 действий и записаны
> до простановки признака. Основание сменилось на 76 — раздел 6,
> пункт 2. Ссылок среди них не осталось: по определению из раздела 1
> действие, заданное через `to`, разрушающим не бывает.

**Признак не отвечает на вопрос 7.2, и разрыв тут двойной.**

1. **Он пофайловый, а не по действию.** Файл может звать `prompt(` для
   одного действия и не звать для другого. 53 — это «в файле, где стоит
   разрушающее действие, где-то есть `prompt(`», а не «у этого действия
   есть подтверждение».
2. **Он не о подтверждении, а о вызове функции с таким именем.**
   Подтверждение может быть сделано иначе, а `prompt(` в файле — стоять
   ради другого действия или не значить ничего.

Поэтому 53 — не «53 действия подтверждаются», и 23 — не «23 действия
опасны без спроса». Это верхняя и нижняя границы, между которыми
поштучной проверки нет. Она требует разбора обработчиков и не проведена
ни 2026-09-02, ни 2026-09-08.

**7.3 Токен красного цвета** для правила 4.3 назначен 2026-09-02 —
`fg-error`, решение
[DEC-011](../decisions/DEC-011-krasnyy-v-menyu-fg-error.md). Зависимость
закрыта.

**7.4 Опознание разрушающего действия машиной.** Простановка признака
закрыта 2026-09-02: помечены 76 действий, вопрос «кто проставит
остальным» снят. Осталась его вторая половина: **линтер не видит
отсутствия признака.** Он проверяет порядок среди тех действий, что
помечены, но не может сказать, что действие помечено не было.

Опознать непомеченное разрушающее можно только догадкой по иконке
и метке — тем способом, которым составлялась опись 2026-09-02. Заводить
по догадке правило контракт не разрешает: это была бы проверка не того,
что записано, а того, что мы предполагаем. Поэтому новое разрушающее
действие без признака пройдёт мимо всех проверок, и поймать его может
только ревью.

**Наблюдение, 2026-09-08: у правила 4.3 есть и вторая слепая зона —
проставленный признак, до которого разбор не дотягивается.** Из 76
пометок правило читает 68. Остальные восемь стоят в списках, которые
собираются в рантайме, и правилу 4.3 недоступны — не потому, что
их не проставили, а потому, что прочесть их нечем.

Семь из восьми — вне тега вовсе: список собран в переменной, в тег
приходит её имя.

| где | в чём собирается |
|---|---|
| `routes/api-key-management/.../api-key-general-section.tsx:106` | `dangerousActions` |
| `routes/api-key-management/.../api-key-general-section.tsx:116` | `dangerousActions` |
| `routes/customers/.../customer-general-section.tsx:90` | `actions` |
| `routes/customers/.../customer-group-section.tsx:225` | `actions` |
| `routes/locations/.../location-general-section.tsx:511` | `countries` |
| `routes/roles/.../role-general-section.tsx:113` | `actions` |
| `routes/products/product-import/product-import.tsx:77` | `uploadedFileActions` |

Восьмая — `routes/orders/order-create-edit/.../order-edit-item.tsx:245`
— стоит внутри тега, но внутри условного элемента
(`...[ !isItemRemoved ? { … } : { … } ]`). Список виден, элемент — нет:
это один из пяти случаев раздела 6, пункт 3.

**Отдельно про `product-import.tsx:77`.** Там разрыв не только в форме
записи. Список `uploadedFileActions` уходит не в меню, а в `FilePreview`
(`:96`), и уже тот подставляет его в своё меню
(`components/common/file-preview/file-preview.tsx:54`). До этого действия
не добраться разбором тега `<ActionMenu` ни при какой форме записи
списка: между пометкой и меню стоит чужой компонент. Считать его
действием меню верно — оно им и станет на экране.

**Что это меняет для 4.3.** Ничего в самом правиле: порядок оно
проверяет там, где видит элементы, и на 90 вызовах нарушений нет.
Меняет чтение результата. «Нарушений порядка нет» относится к 68
пометкам из 76; про остальные восемь правило молчит, и молчание это
того же рода, что в 7.7, — цена формы записи, а не недоработка проверки.

**7.5 Замена проверки 4.5** написана 2026-09-08 — зависимость закрыта.
Правило `action-menu/props-closed` читает объявление `ActionMenuProps`
в одном файле компонента и сверяет состав полей с разделом 3. Это новый
вид правила в линтере: область — один файл, а не дерево вызовов.

Правило заведено под раздел 3, а не под 4.5, и якорем ему служит блок
`ts` раздела 3 — тот же текст, из которого взят список разрешённых
полей. Правило 4.5 покрыто следствием; почему так, сказано в 4.5.

**7.6 Расхождение с копией компонента.** В `packages/plugins/draft-order/`
живёт копия `ActionMenu` с 6 вызовами, вне области линтера и вне этого
контракта. После правок 2026-09-02 у копии и оригинала разный API.
См. [Q-015](../questions/Q-015-kopiya-komponenta-v-plagine.md).

**7.7 Форма записи вызовов, мешающая проверке.** 15 вызовов из 90
не получают ответа хотя бы от одного правила — раздел 6, пункт 3.
Перемерено 2026-09-08: сами 15 не изменились, изменилась база.
Лечится не проверкой, а формой записи в вызовах: литеральный список
вместо переменной (10 случаев) и условие вокруг списка вместо условия
внутри элемента (5 случаев). Решения, править ли их, нет. Вопрос
не праздный: 15 из 90 — это 17% вызовов, по которым контракт молчит.
Доля выросла с 13% не оттого, что вызовов стало хуже: заменённые
кнопками меню все были разбираемыми.
